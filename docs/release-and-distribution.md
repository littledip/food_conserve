# Release & Distribution

Status: **nothing set up yet.** No `eas.json`, no store accounts, no store
identifiers in `app.config.js`. The app runs only through Expo Go today.

Scope: getting builds onto other people's devices. Backend work lives in
[cloud-architecture.md](cloud-architecture.md); this document covers accounts,
build pipeline, versioning, store assets, and compliance.

> Store fees and policies below reflect a point in time and change. Verify
> against Apple and Google's current documentation before relying on any
> figure here.

## 1. Do store accounts actually get required?

**Yes, for anyone but yourself — including your own test devices.**

| | Apple | Google |
|---|---|---|
| Account | Apple Developer Program | Google Play Developer |
| Fee | ~$99 / year | ~$25 one-time |
| Needed for | TestFlight **and** App Store | Internal testing **and** Play |

- **Not needed today.** Expo Go covers current development. The accounts become
  necessary the moment the app has to run on a device you don't control.
- **EAS does not avoid registration.** It builds and submits the binaries; the
  store relationship is still required.
- **Android has a sideload path** — distribute an `.apk` directly, no Play
  account. Useful for a handful of early testers.
- **iOS effectively does not.** Ad-hoc distribution is capped at 100 devices
  per year *and* still requires the paid account. TestFlight is the practical
  route and also requires it.

For a single-household pre-launch app, the cheapest honest path is: Android
internal testing or sideload first, add the Apple account when iOS testers
exist.

## 2. Blockers in the current config

Every row below must be resolved before a store build will even produce an
artifact, let alone pass review. Verified against `app.config.js` as of this
writing:

| Field | Current | Required because |
|---|---|---|
| `ios.bundleIdentifier` | **missing** | Hard requirement for any iOS build; immutable once published |
| `android.package` | **missing** | Hard requirement for any Android build; immutable once published |
| `ios.buildNumber` | **missing** | Must increment on every App Store upload |
| `android.versionCode` | **missing** | Must increment on every Play upload |
| `ios.infoPlist.NSCameraUsageDescription` | **missing** | Review routinely rejects missing or generic camera purpose strings |
| `extra.anthropicApiKey` | **ships in bundle** | Extractable from any installed build — see [cloud-architecture.md §7](cloud-architecture.md) |

Bundle identifier and package name are **permanent**. Pick deliberately —
something like `com.<yourdomain>.foodconserve` — because changing it later
means a new store listing and losing existing installs.

### The app has three different names

| Source | Value |
|---|---|
| `app.config.js` `name` | `food_conserve` |
| README title | Food Conserve |
| Splash screen (`app/_layout.tsx`) | Conserve My Food |

`name` is what appears under the icon on the home screen, so `food_conserve`
with an underscore is not shippable. This needs a single decision before the
first build, and it interacts with deferred decision #10 in

## 3. EAS pipeline

No `eas.json` exists. Minimum useful shape:

```jsonc
{
  "cli": { "version": ">= 12.0.0" },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal"
    },
    "preview": {
      "distribution": "internal",
      "android": { "buildType": "apk" }
    },
    "production": {
      "autoIncrement": true
    }
  },
  "submit": { "production": {} }
}
```

- **`development`** — a dev client build, needed once any native module
  outgrows Expo Go (not yet the case).
- **`preview`** — internal distribution; the APK path is what makes Android
  sideloading to testers easy.
- **`production`** — store builds. `autoIncrement` handles
  `buildNumber` / `versionCode` so the manual fields in §2 stop being a
  recurring chore.

Commands: `eas build --profile production --platform all`, then
`eas submit --profile production --platform all`.

**Secrets**: `ANTHROPIC_API_KEY` is read at build time via `dotenv` in
`app.config.js`. EAS builds don't see the local `.env`, so it would need to be
an EAS secret — but per §2 it should stop being a client-side value entirely.
Resolving the proxy first avoids setting up a secret that then gets removed.

## 4. Versioning and what OTA can carry

Two independent numbers:

- **`version`** (`1.0.0`) — the user-visible marketing version, shared by both
  platforms.
- **`buildNumber` / `versionCode`** — per-upload counters the stores use to
  distinguish binaries. Must strictly increase.

**EAS Update** ships JavaScript and asset changes over the air with no review:
most bug fixes, UI changes, copy, scoring-logic changes. Everything built in
this project so far would have been OTA-eligible.

It **cannot** carry native changes — new Expo modules, SDK upgrades (the
54→57→58 upgrades were all native), permission changes, or anything touching
`app.config.js` plugins. Those need a fresh binary and a review cycle.

Runtime-version policy matters: an OTA bundle must only reach binaries whose
native layer it's compatible with, or the app crashes on launch. Set
`runtimeVersion` to `{ "policy": "appVersion" }` or `"fingerprint"` rather than
leaving it implicit.

## 5. Privacy and compliance

Three items this app specifically triggers.

### Camera

`expo-camera` is used for barcode and receipt scanning. iOS requires a purpose
string (`NSCameraUsageDescription`) explaining *why*, in user-facing terms —
"scan grocery barcodes and receipts to add items to your pantry", not "camera
access required". Generic strings are a common rejection reason.

### Receipt images go to a third party

`services/receiptVisionApp.ts` sends receipt photographs to Anthropic. Receipts
contain purchase history and sometimes partial payment details. This is
third-party data sharing and must be declared in:

- **Apple** — App Privacy details ("Purchases", "Photos or Videos", linked vs.
  not linked to identity, used for App Functionality).
- **Google** — Data safety form, including whether data is transmitted
  off-device and whether it's deleted on request.

A **hosted privacy policy URL** is mandatory on both stores and must state that
images are processed by a third-party model provider.

### Account deletion

Apple requires in-app account deletion for any app offering account creation.
No accounts exist today, so this is not yet applicable — but Cognito (step 4 of
[cloud-architecture.md §10](cloud-architecture.md)) introduces it. Design the
deletion path alongside auth rather than retrofitting it: with an event-sourced
backend, "delete my account" means deciding what happens to the household's
event log when one member leaves.

### Also worth noting

- No crash or error reporting exists. Both the `dayNumber` timezone bug and the
  `lastStreakCheckpointAt` crash were found by reading Metro logs on a
  developer's own device — which does not scale past one user.
- The app has no age-sensitive content, so content rating should be
  straightforward, but Play still requires completing the questionnaire.

## 7. Suggested sequence

1. **Decide the app name, bundle ID, and package name** (§2) — everything else
   depends on these, and two of the three are permanent.
2. **Move the Anthropic key behind the proxy**
   ([cloud-architecture.md §7](cloud-architecture.md)) — avoids shipping a
   build with an extractable key, and avoids configuring an EAS secret that
   would then be deleted.
3. **Add the missing config fields** (§2): identifiers, camera purpose string.
4. **Add `eas.json`** and get a `preview` build onto a real device outside Expo
   Go (§3).
5. **Google Play Developer account**, internal testing track.
6. **Privacy policy page + both stores' data disclosures** (§5).
7. **Apple Developer Program + TestFlight**, when iOS testers exist.
8. **Crash reporting**, bundled with whatever native change comes next.
